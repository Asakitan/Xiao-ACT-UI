## Round 76 — attribute contract audit

### The audit

For each mixin in `gui_modules/sao_gui_*_mixin.py`, AST-walk to
collect `self.X = ...` assignment sites (Store context) and
`self.X` read sites (Load context). Then look for reads that have
no matching assignment anywhere in SAOPlayerGUI or any mixin —
those are potential `AttributeError` at runtime.

### The finding

| Attribute | File | Status |
| --- | --- | --- |
| `self._THEME_OVERLAY_MAP` | dps_theme_mixin | False positive — declared as CLASS attribute in panels_mixin (round 47 relocation); resolves via MRO |
| `self._drag` | float_handlers_mixin | **Real miss** — read by 3 methods, never assigned |

### `self._drag` deep-dive

The 3 methods reading `self._drag['x']` etc:

```python
def _float_click(self, e):
    self._drag['x'] = e.x_root  # ← AttributeError on first call
    ...
def _float_drag(self, e): ...
def _float_release(self, e): ...
```

Initial reaction: forgot to relocate the `self._drag = {'x': 0, 'y': 0}`
init when extracting to the mixin. But:

* `grep -rn 'self._drag = ' sao_gui.py + gui_modules/` returns
  ZERO hits.
* `git show 33f7fdd:sao_gui.py | grep self._drag` confirms the
  bug existed pre-refactor too — `_drag` was never initialized.
* The float button's `<Button-1>` binding in
  `_create_floating_widget` (round 56) is
  `self._float.bind('<Button-1>', lambda e: self._toggle_sao_menu())` —
  it goes DIRECTLY to the menu toggle. None of the three
  `_float_*` handlers are ever wired to a Tk event.

So the three methods are **dead code that's been dead since
before the refactor started**. The refactor faithfully carried
them across mixins (round 56 float_hp → round 58 float_handlers)
without realizing they were unreachable.

### Fix

Removed `_float_click` (6 lines), `_float_drag` (10 lines),
`_float_release` (19 lines) from `float_handlers_mixin.py`. Plus
the 3 mentions in the mixin's module docstring. Total ~36 lines
of confirmed dead code purged. Replaced with a 6-line comment
explaining the deletion.

## Round 77 — Unused-import audit + conservative cleanup

### The audit

For `sao_gui.py` only (the most extracted file, most likely to
have stale imports): AST-walk all top-level Import / ImportFrom
nodes, collect imported names. Then AST-walk everything else
(skipping the Import nodes themselves), collect referenced
Names + base of Attribute access (e.g., `ctypes.X` → `ctypes`).
Anything imported but never referenced is a candidate for removal.

Result: **110 unused imports** out of ~140 in sao_gui.py.

### Conservative cleanup

Did NOT remove all 110:
* Some might be re-exports for `from sao_gui import X` callers.
  Confirmed `main.py` only does `from sao_gui import SAOPlayerGUI`,
  but PyInstaller's static analysis sometimes catches transitive
  references through Lib modules that AST doesn't model.
* Tools / temp scripts can import via reflective `getattr`.

Removed only the 5 clearly-safe lines (truly inert post-refactor):

| Line | Removed | Reason |
| --- | --- | --- |
| `from PIL import Image, ImageDraw, ImageTk, ImageFilter, ImageFont` | 5 names | All 5 used to be needed by `_get_hp_pil_font` (deleted in round 71); no other module-level reference in sao_gui.py |
| `import numpy as np` | 1 | Same — `np` only appeared in `_get_hp_pil_font`'s cache key |
| `from render_capture_sync import wait_until_capture_idle` | 1 | Caller method moved to mixin; no longer referenced at sao_gui scope |
| `from perf_probe import probe as _probe, phase as _phase_trace, gauge as _perf_gauge` | 3 | Used by 7 mixins (each with its own perf_probe import); sao_gui itself doesn't use any of them |
| `import _sao_cy_uihelpers as _CY_UI` | 1 | Same pattern — used by ~10 mixins, each importing it; sao_gui doesn't need it at module scope |

Replaced the 5 import lines with 5 explanatory comment lines.
Net line-count change: 0.

The 96+ remaining "unused imports" stay — they're either:
* Standard lib (`sys`, `math`, `Any`, `Dict`, etc.) — tiny, harmless.
* Engine/overlay/panel classes (`AutoKeyEngine`, `DpsOverlay`, etc.) —
  PyInstaller's static analysis benefits from having them at
  module scope even when not directly referenced.
* `SAOXxx` classes from sao_theme — same concern.

Aggressive removal of the engine/panel imports was deemed too
risky for the marginal cosmetic win.
