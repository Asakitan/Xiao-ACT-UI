## Round 34 — `_compute_boss_hp_delta` extraction

The boss-HP overlay push inside `_push_packet_overlays` was a
single 260-line inline block. It reads `gs` + bridge data + a
handful of `self._bb_*` state, builds an overlay payload dict,
hashes the sig via `_CY_UI.build_boss_bar_sig`, and pushes to
`self._boss_hp_overlay.update(...)`. Pure compute except for the
single `update()` call at the end.

Extracted into a new mixin method `_compute_boss_hp_delta(self,
gs, _pp_now)` that:
* Does all the compute + `self._bb_*` state mutations.
* Returns the dict to pass to `_boss_hp_overlay.update()`, or
  `None` when the sig is unchanged (deduplication preserved).
* Touches no Tk widget — making it safe to call from any thread.

The call site in `_push_packet_overlays` shrunk from a 260-line
inline block to a 9-line helper call:

```python
_bb_payload = self._compute_boss_hp_delta(gs, _pp_now)
if _bb_payload is not None:
    try:
        self._boss_hp_overlay.update(_bb_payload)
    except Exception:
        pass
```

Round-34 outcome: same-thread refactor, no behavioral change,
sets up round 35. State mixin: 770 → 794 lines (+24 net — added
boilerplate of `@_probe.decorate` + docstring outweighs the small
indent-level save).

## Round 35 — daemon worker for the compute

The `_compute_boss_hp_delta` call moved from inline main-thread
to an off-main daemon worker via a **latest-wins single-slot
mailbox** pattern:

```
              ┌──── enqueue (O(1)) ────┐
Tk main loop ─┤                        ├─> daemon worker
              └─── consume (O(1)) ─────┘    (computes delta)
                          ▲
                          │ payload from previous tick
                          ▼
                  _boss_hp_overlay.update(...)
```

### Five new mixin methods

| Method | Purpose |
| --- | --- |
| `_ensure_boss_hp_worker` | Lazy-start the daemon thread on first use |
| `_boss_hp_worker_loop` | Daemon body: wait for signal → compute → store output |
| `_enqueue_boss_hp_compute(gs, now)` | Main → worker: write latest (gs, now) to input slot under lock + signal |
| `_consume_boss_hp_payload()` | Worker → main: read+clear output slot under lock |
| `_stop_boss_hp_worker()` | Clean shutdown (called from `_finalize_close`) |

Mailbox semantics: the input slot only holds the LATEST snapshot.
If main thread enqueues twice before the worker drains, the older
snapshot is dropped. The output slot is set-once-and-clear: main
thread reads the latest computed payload (could be `None` if the
worker hasn't produced one since last consume, or if the sig was
unchanged).

### Latency tradeoff

Main thread now applies the payload computed from the PREVIOUS
tick's `(gs, now)`. At 5 Hz recognition cadence, this is at most
200 ms of latency on the boss-HP overlay. Well below the human
detection threshold (~80-100 ms for visual changes of this kind),
and the boss HP doesn't change semantically faster than humans
read it anyway.

### Thread safety analysis

The compute mutates these `self.X` fields:
* `self._bb_recent_targets` (dict) — also written by packet thread
  (insert on damage). Worker now also pops expired entries.
  Snapshot via `list(self._bb_recent_targets.items())` before
  iterating ⇒ GIL-atomic per CPython.
* `self._bb_last_target_uuid`, `self._bb_last_damage_ts`,
  `self._last_boss_hp_push_sig`, `self._bb_last_hp_motion_sig`,
  `self._bb_last_hp_motion_ts` — scalar/tuple assignment,
  GIL-atomic.

Cross-tick ordering may differ from the pre-worker version, but
the only visible effect is at most one extra "force-push" frame
when a sig race occurs; the next tick's compare absorbs it.

### Shutdown hook

`SAOPlayerGUI._finalize_close` now calls `self._stop_boss_hp_worker()`
before tearing down overlays:

```python
try:
    self._stop_boss_hp_worker()
except Exception:
    pass
```

Safe to call when the worker was never started (no-op via the
`_boss_hp_worker_started` guard).

### Smoke validation

Out-of-process smoke test with a `Mock(SAOPlayerGUIStateMixin)`
that returns `{'mock_payload': N}` from `_compute_boss_hp_delta`:

* Worker thread starts ✓
* 5 rapid `_enqueue_boss_hp_compute()` calls → worker processes
  all 5 in this test (timing-dependent; under contention it would
  drop intermediate snapshots) ✓
* `_consume_boss_hp_payload()` returns the latest payload ✓
* Second consume returns `None` (slot drained) ✓
* `_stop_boss_hp_worker()` kills the daemon within 200 ms ✓

## Round 37+ outlook

The boss-HP block is the LARGEST single compute on the main
thread per tick. Other candidates for off-main:

* **DPS overlay poll** — already centralized via
  `_dps_tracker.poll_overlay_state()` (single lock acquisition);
  the cost is mostly in `_dps_tracker` internals which run on
  the dps event thread anyway. Lower priority.
* **Commander roster diff** — `_push_commander_data` runs at most
  every 300 ms (throttled). Already low-frequency.
* **Player batch info sync** — `_dps_tracker.update_player_info_batch`
  runs at most every 1 s (throttled). Already low-frequency.
* **`_refresh_session_players_panel`** — main-thread Tk widget
  mutations; CAN'T move off-main.

So round 37 is more likely to target additional `SAOPlayerGUI`
mixin splits (menu / fisheye / boss_raid / commander) for the
file-size goal, with one more off-main pass if the user reports
the boss-HP fix wasn't enough.
